# Installing OSM2XP-generated FlightGear scenery

This guide explains how to install scenery generated by OSM2XP in the **FlightGear** output mode into a running FlightGear installation, including the generated airports.

The mechanics described here were verified against the FlightGear / SimGear sources (`apt_loader.cxx`, `NavDataCache.cxx`, `ReaderWriterSTG.cxx`, `newbucket.cxx`, `tilemgr.cxx`, `tileentry.cxx`, `SGBuildingBin.cxx`, `options.cxx`).

---

## 1. What OSM2XP generates

Selecting the **FlightGear** mode produces the following output in the target folder. FlightGear uses sub-bucket tiles (0.125° of latitude per tile, longitude span depending on the latitude band), so a 1°×1° source cell is split into several sub-buckets; every sub-bucket that received content gets its own `Objects/` entry.

Example (tile lat=52, lon=80, source `volchikha.osm.pbf`):

```
<scenery_root>/
├── NavData/
│   └── apt/
│       └── xx00/                     ← one folder per airport (ICAO or synthetic xxNN)
│           └── apt.dat               ← X-Plane apt.dat 1050 format
├── Models/
│   ├── objects/                      ← bundled FlightGear .ac models + textures (3D buildings, see §4)
│   │   ├── house/
│   │   ├── industrial/
│   │   └── ...
│   └── specobjects/                  ← bundled rule-based models (chimneys, cooling towers, see §4)
├── Objects/
│   └── e080n50/                      ← 10° band folder
│       └── e080n52/                  ← bucket folder (top band + degree)
│           ├── 4268928.stg           ← STG scenery script
│           ├── BuildingList_4268928.txt.gz
│           └── LineFeatureList_ws30Road_4268928.txt.gz   ← roads/railways (see §4)
├── Terrain/
│   └── e080n50/e080n52/4268928.btg.gz   ← terrain tiles for the area (downloaded/copied, optionally patched)
└── transportation_report_52.0_80.0.txt   ← roads/rails/powerlines report (informational)
```

| File | Purpose |
| :--- | :--- |
| `NavData/apt/<ICAO>/apt.dat` | One **per-airport** file in **X-Plane apt.dat 1050** format. Folder name is the airport ident (real ICAO or synthetic `xxNN`). |
| `Models/objects/…`, `Models/specobjects/…` | Bundled FlightGear `.ac` models (converted from the X-Plane `.obj` originals, and their textures/LIT files) that the generated STG references via `OBJECT_SHARED_AGL`. Copied automatically by OSM2XP into the output root (see §4). |
| `Objects/<band>/<bucket>/<index>.stg` | Scenery tile script for one FlightGear sub-bucket (see §4). File name is the bucket index, e.g. `4268928.stg`. |
| `Objects/<band>/<bucket>/BuildingList_<index>.txt.gz` | OSM building list referenced by the STG file, placed next to it. |
| `Objects/<band>/<bucket>/LineFeatureList_<material>_<index>.txt.gz` | Road/railway list files referenced by `LINE_FEATURE_LIST` STG tokens (one file per material per bucket, see §4). |
| `Terrain/<band>/<cell>/<index>.btg.gz` | Terrain tiles covering the generated area. They are copied from the configured scenery root or downloaded from TerraSync, and patched when airfield BTG patching is enabled. Present only when terrain was prepared for the run (building elevation, airfield patching or forests). |
| `transportation_report_<lat>_<lon>.txt` | Validation report for roads/railways/powerlines (informational, kept at the scenery root). |

Example `NavData/apt/xx00/apt.dat` (Volchikha test area):

```
I
1000 Version - generated by OSM2XP 1.0.0-SNAPSHOT

1 669 0 0 xx00 Volchikha Airport
1302 flatten 1
1302 datum_lat 52.500000
1302 datum_lon 80.500000
100 ...   (runway)
102 H1 ... (helipads)
110 ...   (apron/pavement)
130 xx00  (airport boundary)
99
```

## 2. How FlightGear finds scenery

FlightGear searches a list of **scenery roots**, in order:

1. Paths given with `--fg-scenery` (repeatable),
2. paths from the `FG_SCENERY` environment variable,
3. the TerraSync directory,
4. `$FG_ROOT/Scenery` (added automatically only if no path was given above).

Scenery is organized in **sub-bucket tiles**. A tile is stored as:

```
<scenery_root>/<suffix>/<bucket_path>/<bucket_index>.stg
```

- `<bucket_path>` is a two-level folder derived from the tile's base latitude/longitude, e.g. `e080n50/e080n52` for lat≈52, lon≈80 (10° band + actual degree).
- `<bucket_index>` is a numeric tile id, e.g. `4268928.stg` for the bottom-left sub-tile of the 80..81°E, 52..53°N degree cell.
- `<suffix>` is one of the configured scenery type folders. The defaults are `Objects` and `Terrain`; the full list is configured in `$FG_ROOT/options.xml` under `/sim/rendering/scenery-path-suffix`. `.stg` files conventionally live under `Objects/`.

> Scenery files placed directly in a scenery root (flat, no type sub-folder) are **no longer supported** by FlightGear and are skipped with a warning.

Airport/navigation data is loaded separately from any scenery root. FlightGear scans `NavData/apt/` **recursively** for `*.dat` / `*.dat.gz` files, so per-airport sub-folders such as `NavData/apt/<ICAO>/apt.dat` are picked up automatically:

```
<scenery_root>/NavData/apt/<ICAO>/apt.dat        (plain)
<scenery_root>/NavData/apt/<ICAO>/apt.dat.gz     (gzipped, optional)
```

plus the default file `$FG_ROOT/Airports/apt.dat.gz`. Files found in scenery roots are read **before** the default file, so a custom `NavData/apt` airport takes precedence over the shipped one. If several files define the same airport identifier, the **first one wins** (the folder name is only for humans — FlightGear reads the ident from the `1 <id> …` header row).

## 3. Installing the airports (fully supported)

The generated `NavData/apt/<ICAO>/apt.dat` files are directly consumable by FlightGear. The row codes used (`1`, `100`, `102`, `110`, `111/113`, `130`, `99`) and their field layout match what `apt_loader.cxx` expects; the `1302 flatten/datum` rows are safely ignored.

**Step-by-step**

1. **Copy the whole `NavData` folder into a scenery root:**
   - Result: `<scenery_root>/NavData/apt/<ICAO>/apt.dat` (one file per airport).
   - Optionally gzip each file (`gzip -9 apt.dat`) so it becomes `apt.dat.gz` — FlightGear reads both.

2. **Add that scenery root to FlightGear.** Pick one:
   - Launcher: *Settings* → scenery paths (add the folder).
   - Command line: `--fg-scenery="<scenery_root>[,<other_root>]"`
   - Environment variable: `FG_SCENERY="<scenery_root>"`
   - Tip: you can also drop the folder under `$FG_ROOT/Scenery/NavData/apt/` to avoid changing any settings (the shipped `$FG_ROOT/Scenery` folder is scanned automatically).

3. **Let the navigation cache rebuild.** FlightGear caches parsed airport data in a SQLite cache (`$FG_HOME/navdata_<major>_<minor>.cache`). It detects new/changed `apt.dat` files automatically (file list + modtime + hash) and rebuilds on the next start. To force a rebuild:

   ```
   FG_NAVCACHE_REBUILD=1 fgfs ...
   ```

   (`$FG_HOME` is typically `~/.fgfs` on Linux, the FlightGear app-data folder on Windows/macOS.)

4. **Start at the airport.** Airports without a real ICAO get a fake identifier (`xx00`, `xx01`, …). Start there with:

   ```
   fgfs --fg-scenery="<scenery_root>" --airport=xx00
   ```

   You can also type the identifier into the *Location* section of the FlightGear Launcher.

**What you get:** runways (`100`) with surface/lights, helipads (`102`), apron/pavement polygons (`110`), and the airport boundary (`130`), all rendered from the `apt.dat` data. Note that the `1302 flatten` rows are X-Plane metadata that FlightGear ignores, so the terrain underneath is *not* flattened by this file.

**Identifier caveats**

- The generated identifiers use an `xx` prefix (e.g. `xx00`), which is not a real ICAO. If the OSM data provides an ICAO (`icao` tag), that value is used instead.
- Because "first definition wins", another scenery package that already defines the same identifier will suppress yours. Prefer a fresh scenery root listed before TerraSync in the scenery-path order.

## 4. Installing the OSM scenery layer (buildings/objects)

Since OSM2XP now writes each sub-bucket's STG directly into the correct `Objects/<bucket_path>/` folder (with its building list next to it), the **manual bucket-merging step is no longer needed**: just copy the generated `Objects/`, `Models/` and (when present) `Terrain/` folders into the scenery root.

The `.stg` files contain:

- one `BUILDING_LIST <file> <material> <lon> <lat> <elev>` token referencing the `BuildingList_<index>.txt.gz` in the same folder (renders OSM buildings as instanced building geometry),
- `OBJECT_SHARED_AGL <model> <lon> <lat> ...` lines for rule-matched 3D objects (cooling towers, chimneys, lighthouses, water towers) and, when `generateBuildings3D` is enabled, for building-size 3D houses. The `<model>` path is **scenery-root-relative** (e.g. `Models/specobjects/chimney-100.ac`, `Models/objects/house/R_9.84x6.80.ac`), so it only resolves if the matching files exist under `<scenery_root>/Models/`,
- `LINE_FEATURE_LIST <file> <material>` tokens referencing the road/railway list files (see below),
- powerlines written as `# ...` comment metadata (they are **not** rendered as meshes yet).

The generated STG files contain **no `OBJECT_BASE`** — OSM2XP does not generate terrain. Instead, when terrain is needed (building elevation, airfield BTG patching or forests) OSM2XP prepares it before the main pass: tiles are reused from the `source_tiles` cache, else copied from the configured `flightGearSceneryPath`, else downloaded from the TerraSync mirrors, and every tile for the area is copied into the generated `Terrain/` folder (patched if airfield patching is enabled). Buckets outside the generated area still come from another terrain source — normally TerraSync or `$FG_ROOT/Scenery` — so keep such a root **after** your overlay root in the search order.

**Step-by-step**

1. **Copy the generated `Objects/`, `Models/` and (if present) `Terrain/` folders into a scenery root** (or point the scenery root directly at the OSM2XP target folder). Result: `<scenery_root>/Objects/e080n50/e080n52/4268928.stg`, `<scenery_root>/Models/specobjects/cooling_tower-100.ac`, `<scenery_root>/Terrain/e080n50/e080n52/4268928.btg.gz`, etc.
   - `Models/objects/` holds the building-size 3D models (used only when `generateBuildings3D` is enabled); `Models/specobjects/` holds the rule-based models (chimneys, cooling towers, …). Textures/`.png`/`.dds` and `_LIT` night files sit alongside the `.ac` files and must be copied with them.
   - OSM2XP copies these folders automatically into its output root at generation time, so a full copy of the output root is all you need.

2. **Make sure a terrain source is available for buckets outside the generated area** (TerraSync enabled, or the bucket exists in `$FG_ROOT/Scenery`), ordered **after** your overlay root in the scenery-path list. Buckets inside the generated area already have their terrain in the generated `Terrain/` folder.

3. Restart FlightGear (or reload scenery). Buildings appear from the `BUILDING_LIST` data using the `OSMBuildings` material from FlightGear's material database; the `OBJECT_SHARED_AGL` models are loaded from `<scenery_root>/Models/`.

> If a sub-bucket received no content, OSM2XP writes nothing for it — that bucket simply uses the terrain root as-is.
>
> If a referenced model is missing under `<scenery_root>/Models/`, FlightGear logs a "failed to load model" warning and skips that object. Keep the whole `Models/` folder together with the `Objects/` folder in the same scenery root.

### Building ground elevation

Building positions are written as **local Cartesian metres** relative to the STG `BUILDING_LIST` anchor (X south, Y east, Z up) with the round-Earth sagitta correction, exactly as FlightGear's `SGBuildingBin` expects. Their **vertical placement** depends on the terrain elevation at each building.

By default OSM2XP probes elevation **in-process** from the prepared BTG tiles: the `source_tiles` cache (filled by the terrain pre-pass from the configured scenery root or from TerraSync) is indexed with a per-tile spatial hash and queried with barycentric interpolation, so no external tool is needed and buildings are terraced to the real terrain. This is the same data FlightGear renders, and it works offline once the tiles are available.

`fgelev` is only a **last resort**: it is used when no in-process terrain index can be built (for example for a terrain format whose reader is not implemented yet). In that case OSM2XP spawns `fgelev --use-vpb --tile-file <tile.btg.gz>` (one process per sub-bucket, capped by an LRU pool of 32) and queries it over stdin/stdout.

Configuration in `flightgear/FlightGearOptions.xml`:

- `generateBuildingsElevation` = `true` (default) — enable ground elevation probing;
- `flightGearSceneryPath` — an existing FlightGear scenery root used as a local terrain source before downloading (optional, but recommended);
- `fgelevPath` — path to the `fgelev` executable; only needed for the fallback path;
- `terrainMirrors` — TerraSync mirrors used to download missing tiles (defaults are built in).

Terrain tiles are cached in `source_tiles` under the working folder (falling back to the folder of the input file, then the OS temp folder), so subsequent runs do not download them again. Buildings over water/void (`-9999`/`-1000`) or on terrain without a tile are skipped. If no terrain can be obtained at all, generation still works, but buildings sit at the anchor elevation.

To pre-fetch tiles for a region without running the generation (e.g. to seed the scenery path), you can still use the standalone tool (JDK 11+, single-file source launch):

```
java tools/DownloadFgTerrain.java --bbox "77.4,51.2,88.5,56.1" --root D:/Work/fg_scenery
```

### Roads and railways (LINE_FEATURE_LIST)

Roads and railways are written as real FlightGear scenery using **`LINE_FEATURE_LIST`** list files (the same mechanism as OSM2City and TerraSync):

- one gzipped list file per **material** per sub-bucket, e.g. `LineFeatureList_ws30Road_4268928.txt.gz`, placed next to the STG file;
- each row is one OSM way in the SimGear format `W <width> <lit> <A> <B> <C> <D> <lon> <lat> …` (width in metres, attributes `1 1 1 1`, coordinates in WGS84 degrees);
- the STG file gets one `LINE_FEATURE_LIST <file> <material>` token per material used in that bucket.

Materials map as follows (all are shipped by FlightGear in `Materials/base/materials-base.xml`, referenced from the default `global.xml`):

| OSM data | Material |
| :--- | :--- |
| `highway=motorway`, `trunk` (+ their `_link` variants) | `ws30Freeway` |
| all other supported `highway=*` values | `ws30Road` |
| `railway=rail/tram/light_rail/subway/narrow_gauge/preserved/disused` | `ws30Railway` |

**Important:** `LINE_FEATURE_LIST` is only processed by the **VPB terrain pipeline** (FlightGear ≥ 2020.3, i.e. the default "new" WS30 terrain). It is ignored on the legacy WS2.0/WS20 tile set, and there is no elevation probing for wires — the features are draped onto the terrain automatically.

**Known limitations (current state of the FlightGear output)**

- Power lines are exported as comment metadata only (`# powerline …`); there is no dedicated FlightGear cable material, so they are not rendered yet (a 3D/glTF approach like modern OSM2City is a possible follow-up).
- Roads/railways render only on VPB terrain (FlightGear ≥ 2020.3); on legacy WS2.0 tiles the `LINE_FEATURE_LIST` tokens are ignored.
- The generated STG has no `OBJECT_BASE`; buckets outside the generated area still need terrain from a later scenery root, otherwise they render as ocean.
- Building ground elevation is accurate when the terrain tiles are available (they are prepared automatically); without terrain, buildings sit at the anchor elevation.

## 5. Troubleshooting

| Symptom | Cause / Fix |
| :--- | :--- |
| Airport not selectable in the Launcher | Navigation cache not rebuilt yet; start once with `FG_NAVCACHE_REBUILD=1`, or delete `$FG_HOME/navdata_*.cache`. |
| Airport identifier taken over by another package | Another `apt.dat` defined the same identifier first. Use a fresh scenery root ordered before TerraSync, and/or make sure the OSM `icao` tag produces a unique ident. |
| "Found scenery file … no longer supported" | A `.stg` was placed flat in a scenery root. With the current output this should not happen — STGs are written to `Objects/<bucket_path>/`. If you copied files manually, move them into `<scenery_root>/Objects/<bucket_path>/`. |
| "Building specifies unknown material: OSMBuildings" | The `OSMBuildings` material is missing/renamed in the loaded material database. Keep the default FG data or use a material name that exists in `Materials/ground/materials.xml`. |
| 3D objects (chimneys, cooling towers, houses) missing / "failed to load model" warning | The `OBJECT_SHARED_AGL` model path is scenery-root-relative, so the referenced `.ac` must exist under `<scenery_root>/Models/`. Re-copy the generated `Models/` folder into the same root as `Objects/`, or re-enable the `generateObjects`/`generateBuildings3D` option and regenerate. |
| Roads/railways not visible | `LINE_FEATURE_LIST` requires the VPB terrain pipeline (FlightGear ≥ 2020.3 / WS30 terrain). On legacy WS2.0 tiles the tokens are silently ignored. Check the FG console for a "specifies unknown material" warning if `ws30Road`/`ws30Freeway`/`ws30Railway` are missing from the material database. |
| Tile renders as ocean / no terrain | The STG has no `OBJECT_BASE` and this bucket is outside the generated area, so no `Terrain/` tile was produced and no later scenery root provides it. Keep the real tile (TerraSync / `$FG_ROOT/Scenery`) in the search path after your overlay root. |
| Buildings at wrong height / all at sea level | No terrain was available for the area, so elevation probing was skipped. Make sure the terrain pre-pass can copy tiles from `flightGearSceneryPath` or download them from `terrainMirrors`. `fgelev` is only a fallback and is not required for BTG. |
| Building elevation probing disabled warning | OSM2XP logs this when no terrain index could be built for the area (no cached or scenery tiles). Generation continues with buildings at the anchor elevation; `fgelev` is only a last resort. |

## 6. Reference

- apt.dat format compatibility with FlightGear: [`spec/apt_xplane_vs_flightgear.md`](../spec/apt_xplane_vs_flightgear.md)
- apt.dat row codes emitted by OSM2XP: `1` (airport), `100` (runway), `102` (helipad), `110` + `111/113` (pavement), `130` + `111/113` (boundary), `99` (end), `1302` (ignored by FlightGear).
- Scenery options: `--fg-scenery` (repeatable), `FG_SCENERY`, `--airport=<ident>`.
- Cache override: `FG_NAVCACHE_REBUILD=1`.
